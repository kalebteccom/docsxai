<div class="docsx-section not-content">
  <h2 class="docsx-section-title">Why it exists</h2>
  <div class="docsx-section-sub">
    Screenshot docs rot the moment the UI moves. docsxai treats them as a
    build artifact: a written flow is the source, the rendered doc pack is
    the output, and a re-run is the refresh.
  </div>

  <div class="docsx-grid">
    <div class="docsx-card">
      <span class="docsx-card-mark">// execution</span>
      <h3>Deterministic CI replay</h3>
      <div class="docsx-card-text">
        A frozen clock and a pinned locale, timezone, and viewport: the same
        flow against the same target state produces byte-identical
        screenshots. <code>run --verify-determinism</code> runs a flow two to
        five times and names the first artifact that differs, and
        <code>diff --fail-on warn</code> gates CI on drift against a
        committed baseline.
      </div>
    </div>
    <div class="docsx-card">
      <span class="docsx-card-mark">// variants</span>
      <h3>One flow, many variants</h3>
      <div class="docsx-card-text">
        A <code>matrix</code> block expands a flow file into one run per
        locale, color scheme, and viewport, up to 64 combinations.
        <code>pack</code> builds the screenshot pack from them and
        <code>pack --check</code> compares it with the committed one.
      </div>
    </div>
    <div class="docsx-card">
      <span class="docsx-card-mark">// calibration</span>
      <h3>Agent calibration, any MCP host</h3>
      <div class="docsx-card-text">
        An agent authors the flow-file once, through the Claude Code plugin
        or the standalone MCP server, with lint, diagnose, and actionability
        probes at write-time. After that, every run is agent-free: no model
        in the loop, no token bill per refresh.
      </div>
    </div>
    <div class="docsx-card">
      <span class="docsx-card-mark">// output</span>
      <h3>One doc pack, three deliveries</h3>
      <div class="docsx-card-text">
        An interactive viewer with halos and callouts, an Astro Starlight
        site, or burned captions in plain PNGs for places that cannot run
        the viewer. Redactions mask sensitive UI before any pixel hits
        disk. The text the viewer and the site add comes in English or
        Spanish, set with <code>--lang</code>.
      </div>
    </div>
    <div class="docsx-card">
      <span class="docsx-card-mark">// captions</span>
      <h3>Themeable burned captions</h3>
      <div class="docsx-card-text">
        The halo, numbered badge, callout, and connector follow a
        <code>burn.theme</code> block: four presets (clean, soft,
        high-contrast, readable), an optional design-tokens file, and per-key
        overrides. The interactive viewer reads the same theme. The
        <code>readable</code> preset scales captions with the screenshot, and
        <code>display_width</code> takes a second width for narrow captures,
        so a phone capture and a desktop capture both read at 15 px. A themed
        burn joins each caption to its target with a 2 px line and can fall back
        to a numbered badge where no clear spot exists. New in the next
        release.
        <a href="/guides/burn-theming/">Read the burn theming guide</a>
      </div>
    </div>
    <div class="docsx-card">
      <span class="docsx-card-mark">// plugins</span>
      <h3>Publishers and renderers as plugins</h3>
      <div class="docsx-card-text">
        Publishers, renderers, lint rules, and auth strategies extend the
        engine through a namespaced, capability-declared, sha256-locked
        runtime. First-party publishers cover Confluence, GitBook, Guru,
        Notion, and SharePoint. SharePoint is on npm as an
        experimental package since 0.3.0-rc.3. The others are repo-only for now.
      </div>
    </div>
  </div>
</div>

<div class="docsx-section not-content" id="first-run">
  <h2 class="docsx-section-title">First run</h2>
  <div class="docsx-section-sub">
    Five steps, about ten minutes, against an app running on your machine. Each step shows a line
    you should see.
  </div>
  <ol class="docsx-steps" role="list">
    <li class="docsx-card docsx-step">
      <span class="docsx-card-mark">// step 1</span>
      <h3>Make a workspace</h3>
      <CopyCommand
        command="docsxai init my-docs --app-url http://localhost:3000 --auth none"
        label="Copy the init command"
      />
      <div class="docsx-card-text">
        Creates the folder docsxai writes into and saves your app's address in{" "}
        <code>my-docs/.docsxai.json</code>. Keep it outside your app's repo. If the app needs a
        login, leave out <code>--auth none</code> and run <code>docsxai capture-auth my-docs</code>{" "}
        before step 3.
      </div>
      <p class="docsx-expect">
        <span class="docsx-expect-label">Expect</span>
        <code>
          {
            "created: flows/, docs/, auth/, .auth/, .viewer/, .gitignore, .docsxai.json, flows/example.flow.yaml.sample, README.md"
          }
        </code>
      </p>
    </li>
    <li class="docsx-card docsx-step">
      <span class="docsx-card-mark">// step 2</span>
      <h3>Check the setup</h3>
      <CopyCommand command="docsxai doctor my-docs" label="Copy the doctor command" />
      <div class="docsx-card-text">
        Checks Node, Chromium, the config, write access and <code>app_url</code>. A failing line
        names its fix after <code>next:</code>.
      </div>
      <p class="docsx-expect">
        <span class="docsx-expect-label">Expect</span>
        <code>{"ok: config: .docsxai.json fields are valid"}</code>
      </p>
    </li>
    <li class="docsx-card docsx-step">
      <span class="docsx-card-mark">// step 3</span>
      <h3>Calibrate with an agent</h3>
      <CopyCommand
        command={"/plugin marketplace add kalebteccom/docsxai\n/plugin install docsxai@docsxai"}
        label="Copy the Claude Code plugin commands"
      />
      <div class="docsx-card-text">
        With the plugin installed and your app running, ask Claude Code in plain words, for example
        "calibrate my-docs: open the Reports page and show the export button". It writes the flow
        into <code>my-docs/flows</code> once, and every run after that needs no agent.
      </div>
      <p class="docsx-expect">
        <span class="docsx-expect-label">Expect</span>
        <code>{"next: docsxai run my-docs  (then: docsxai render my-docs)"}</code>
      </p>
    </li>
    <li class="docsx-card docsx-step">
      <span class="docsx-card-mark">// step 4</span>
      <h3>Run it</h3>
      <CopyCommand command="docsxai run my-docs" label="Copy the run command" />
      <div class="docsx-card-text">
        Replays the flow in headless Chromium and writes annotations and screenshots under{" "}
        <code>my-docs/docs</code>.
      </div>
      <p class="docsx-expect">
        <span class="docsx-expect-label">Expect</span>
        <code>{"run: 1 of 1 flow ok, outputs in my-docs/docs"}</code>
      </p>
    </li>
    <li class="docsx-card docsx-step">
      <span class="docsx-card-mark">// step 5</span>
      <h3>Open the docs</h3>
      <CopyCommand command="docsxai render my-docs" label="Copy the render command" />
      <div class="docsx-card-text">
        Builds the interactive viewer into <code>my-docs/.viewer</code> and prints the page to open
        in your browser. Hover, tap or tab to a halo to read its callout.
      </div>
      <p class="docsx-expect">
        <span class="docsx-expect-label">Expect</span>
        <code>{"render: open /path/to/my-docs/.viewer/index.html"}</code>
      </p>
    </li>
  </ol>
